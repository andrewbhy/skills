# jig-review

For a build plan, use [plan mode](plan-mode.md) instead of diff mode. Its fixed signals and checklists select independent seats, always including testing, cost and history. Each plan seat proposes tier 1 or 2 discipline measures from [measures.md](measures.md); product proposes a measurable proxy for every tier 3 goal by Goal ID. Record the ambiguity line in the plan-check outcome. This addition is draft pending coordinator-owned fresh two-provider scenarios.

Coordinate review; add only what built-in correctness review lacks. Prefer the simplest design that works and reuse existing checks.

Severity measures harm: **Critical** — widespread irreversible loss (e.g. deleting production customer data); **High** — a core flow fails (e.g. a command cannot start after a stale import); **Medium** — a bounded contract or policy fails (e.g. a dependency range breaks exact pinning); **Low** — a minor maintenance defect (e.g. a misleading comment). Assess actual impact, separately from priority. When severity is borderline, state the harm in one line and choose the level using the closest rubric example above; explain any difference in scope or reversibility.

Start: run `node "${CLAUDE_PLUGIN_ROOT}/skills/jig-review/telemetry.mjs" start "<project-root>" <provider>`; retain the printed run ID (`off` means disabled).

Before work, read [missed-problems.md](missed-problems.md) and run
`node "${CLAUDE_PLUGIN_ROOT}/skills/jig-review/missed-problems.mjs" --area <area>` from the project root
for every affected area: design, runner, skills or "product slice". Read each
relevant incident; carry one brief line and the printed named check into this
job, then give the check an executable command or a review assertion and evidence.
Explain exclusions. Open repeats block the next round of that work until an
incident-linked rule review under docs/results/ explains what rule failed and
what changes. Missing history or unclassified legacy rows are evidence gaps,
never a clean history. Use jig-correct to record and classify new incidents;
update the same incident rather than duplicating it and preserve its source.

1. **Triage first.** Read the task, acceptance checks, diff and applicable rules/ADRs. Record base and exact committed revision, uncommitted changes excluded from that comparison, and [VERSION](VERSION). Run `node "${CLAUDE_PLUGIN_ROOT}/skills/jig-review/diff-signals.mjs" <base> <revision>` from the project repository; read [config.md](config.md) for configuration and output. On failure, report triage incomplete; never treat missing signals as an empty diff. Classify as trivial, mechanical, refactor, behaviour or risky, highest applicable class winning. Keep at least the script's class floor and every required seat; judgement may raise either. Explain each decision in one line. State who reviews (AI alone or a person too), selected and skipped seats with reasons, and a merge suggestion with its reason. For a person, name the file and line and precise question needing judgement. A safe-without-person suggestion requires all required checks to pass and an existing standing rule allowing that class; otherwise make it conditional. It grants no authority. Let the person correct triage or add seats; flag removal of a fixed required seat as an unmet check, never silently lower it. Treat money, pricing and billing changes as at least risky, alongside public contracts, security, data and concurrency; choose product for behaviour or business-rule changes, not a pure rename or refactor.
2. **Use built-in review.** Request independent correctness review of that exact revision, preferably from the other provider; with one provider, require a fresh session. For complex or risky changes (including fixed large-diff signals), request both providers' built-in reviews. Use only already authorized sessions; hand the launcher the revision and review request if a new session needs authorization. Say which actually ran and which are unavailable or pending. Do not recreate their correctness review or claim independence from a same-session pass. Supply task, relevant rules and ADRs, and keep their findings for the report.
The builder never grades its own output. The coordinator may triage findings but never accepts; acceptance needs a fresh seat distinct from builder and coordinator, seeing the rendered evidence and actual reference. Explaining a finding away as noise requires that fresh seat's agreement and a linked checker calibration item. Every UI seat sees the shared scripts' renders and measurements, not only code; a self-check is evidence, never independent acceptance. Keep Visual craft, Fidelity, Content stress, Motion and Accessibility catalogues separate; a catalogue not reached or not applicable is one line saying why, and each Not tested item is listed once, in the closing report. If independent context or rendered evidence is unavailable, leave that seat pending and name the gap.

3. **Run chosen seats.** Give each seat the same diff and relevant context once, in a fresh context when available and authorized; otherwise run sequentially and disclose that limitation. Keep a separate catalogue for each seat, even an empty one. Require evidence, impact, a file and line or the exact rule/ADR broken, severity (Critical, High, Medium, Low), and priority (before merge, soon, later) for every issue. Label unverified suspicions as gaps rather than established findings. Check only concerns the diff touches:
   - **QA:** use `jig-verify` for observable contracts, boundaries, failure paths, detection proof and proportionate executed checks. Disclose if unavailable.
   - **Product:** compare the change with the task's acceptance checks, business rules, domain edge cases and real-user expectations, and the product vision/principles named in project configuration. Read those documents. Missing acceptance or vision is a gap to resolve, never an invented requirement or a product pass.
   - **Visual craft:** run the shared `visual-check.mjs` runner on declared states. Own deterministic geometry, alignment, containment, visibility, spacing and style findings; retain its grouped report and annotated checkpoint sheet.
   - **Fidelity:** compare that annotated sheet pairwise with the reference and approved baseline in a fresh context, never the builder's session. Fixed rubric: hierarchy, type, spacing, shape, surfaces, colour roles and component states. For each applicable row report better/same/worse, the exact reference/baseline pair, visible evidence and unexplained drift. Do not grade a contact sheet from memory or code. Missing renders, reference, approved baseline or independent context leave this seat pending; a look probe can compare references while explicitly recording that no approved baseline exists yet. See Provider notes for model selection.
   - **Content stress:** exercise Worst case, Empty, One and Many through the same renderer. Check plurals, long/unbreakable strings, missing optional values and supported maximum volume at configured widths and a CSS text-scaling fixture (not native browser zoom). Cite the shared runner's state measurements and renders for each break.
   - **Motion:** review shared `visual-motion.mjs` frame strips and runner measurements for cause then effect, jumps, interruption and equal noticeability in light and dark. Measurements alone do not establish feel; missing frame or next-day review is a gap. If the diff changes no animation, transition or timing, the catalogue is complete as one line: "No changed motion", citing the diff evidence; it is not a pending seat.
   - **Security:** check trust boundaries, secrets, input handling, auth and permissions; for dependencies, inspect maintenance, licence, size, transitive surface and exact pinning.
   - **Accessibility:** check semantics, roles, names, labels and keyboard use; favour controls discoverable by role and accessible name over test-only IDs.
   - **Architecture:** inspect the surrounding application as well as the diff: simplicity and what can be deleted, consistent patterns, boundaries and dependency direction, one owner for state, coupling, maintainability, dependency cost, contracts/rollback, failure handling, operability without secrets, measured performance and testability. Under testability, flag new tests without a named risk, an over-budget suite, new end-to-end or live tests a lower layer could cover, and live checks that should become unit/replay integrations. Run `node "${CLAUDE_PLUGIN_ROOT}/skills/jig-review/test-budget.mjs" -- <fast-test-executable> [args...]` with the project's `.jig/testing.json` budget, tags and globs ([format](testing.md)); missing execution or unsupported discovery is a gap. The maintainer reviews the live set at system-version changes or above three tests, keeping only risks requiring live evidence. Select relevant concerns; name the ADR broken or propose changing the record.

   When review learns of a problem found after tests passed, add or update its incident in docs/missed-problems.jsonl (format in testing.md): stable ID, area, class, date, what happened, who found it, source (script, model or person), lowest layer that should have caught it or person only, and action taken (fix, test layer, rule change). Mark repeats by area and class and block the next round until an incident-linked rule review is written. At each slice end or repeat, the coordinator uses `--summary` on that budget run to gather numbers, compares earlier reports, and saves what works, rules to change and tests to delete in the project's docs/results/ for the person to decide. This rules report is separate from the optional review artifact below.

Before reporting, compare every claim in the proposed commit message with the actual diff. Require executable wiring for claims that a tool runs; adding a file or licence alone is not evidence. Flag unsupported claims and name the missing diff evidence (history: mp-2026-11-08-04, claimed-not-built).

4. **Merge catalogues.** Deduplicate the same fault without losing its discovering seats or built-in reviewer. Show one short report grouped Critical, High, Medium, Low; keep severity (harm) separate from priority (when). A Low finding never blocks alone. Include triage and its reasons, revision, checks actually run, missing evidence, human focus questions and unresolved before-merge findings. Say explicitly when no issues were found, with the limits of that claim. Save the review artifact only if the person opts in: a short Markdown report and JSON counterpart to the configured project-relative report directory (default `.jig/reviews/`); include revision, triage, findings with source (script/model/person), seats/severity/priority/location/evidence, and gaps. Never approve, merge or deploy.

End: run `node "${CLAUDE_PLUGIN_ROOT}/skills/jig-review/telemetry.mjs" end "<project-root>" <provider> <run-id> <passed|failed|stopped|partly>` before reporting; disclose marker failures. Use failed for established unresolved before-merge defects, partly for missing required review/evidence, stopped for an interrupted review, and passed only when required review completed without unresolved before-merge findings. Passed describes review completion, never approval. Provider token counts come from provider records; unknown stays unknown.

## Retro signals

Own rejection, measure-mismatch and confusion. Route stop-rule escalation to
jig-orchestrate. In the same reply turn as the person's rejection/correction, a passing measure
with a failing verdict, or a request to explain shown work, call signals.mjs
beside this skill with the matching kind. Read signal-kinds.md for ownership;
do not duplicate a tool's automatic record or the same incident. Keep cost
when known, planLink/detailLink when available, and ownErrorShare for the
coordinator's share. jig-orchestrate records later escalation decisions; do not duplicate them. Record project or
environment details in that project's private log, never the jig home log.
The helper supplies repeatOf for recurrences. Unknown cost stays absent.

## Provider notes

- **Fidelity model:** use a fresh authorized Sonnet context for the pairwise rubric, never the builder's session. This applies whichever provider builds the change. If unavailable, keep Fidelity pending; do not silently substitute the builder or launch a provider session.

- **Codex:** use `codex` for telemetry; load `.agents/skills/jig-review/`. Built-in correctness review is `/review`. Request Claude Code `/code-review` on the same revision for independence; for risky/complex changes request both. A fresh Codex session is the one-provider fallback. An authorized subagent can give a seat its own context; it does not substitute for the independent built-in review.
- **Claude Code:** use `claude` for telemetry. The generated `.claude/skills/jig-review/SKILL.md` points to this source; resolve supporting files here. Built-in correctness review is `/code-review`. Request Codex `/review` on the same revision for independence; for risky/complex changes request both. A fresh Claude Code session is the one-provider fallback. The Task tool can isolate a seat when authorized; otherwise catalogue seats sequentially.
- **Both:** built-in command availability and scope can differ. If the command cannot review the selected committed revision, report the gap; never substitute a different diff without saying so. Do not launch another provider session without authorization. Use existing project tools; do not install integrations to conceal missing review capability.
